### Recommended first extraction step

- **No new core extraction recommended immediately.** First repair B1/B2, cover shared changes, and take B6/B9 behavior choices; these produce more value than adding a JS boundary now.

The first *new* candidate is the normalized window-policy slice above: start with overlay refusal priority, born-fullscreen hold and admission-clear eligibility, using Windows' existing pure predicates and matched KDE fixtures. Expand to sticky-origin policy only if the Mac implementation needs it. S initial slice / M integration; no universal window state machine.

Actually removing KDE duplication requires a separately approved route or mirror/artifact strategy; until then, matched fixtures establish equivalence, not a single runtime authority. Do not claim K2/AR6 complete merely because Rust policy exists.

- Evidence: **V** means current project source/fixtures read; **R** means historical records only; **TBD** means not established. These questions select no minimum/maximize implementation. User-approved delivery/order/extraction timing is recorded in [decisions](../../decisions.md#engine-architecture-and-convergence).

### Q2. Does a too-large window need to launch floating?

- **No. Floating is an optional fallback, not a necessity proved by our Engine.** It redistributes available space within the chosen tree, without searching other arrangements/axes/targets. A leaf being overconstrained does not prove that no alternative layout could fit it. If its own minimum exceeds the entire usable work area, floating cannot make it fit on-screen either.
- **Current [V]:** neither target automatically floats it. Core leaves proportional fallback allocations and flags leaves violating meaningful minimums (`crates/tiler-core/src/size_hints.rs:250-304,310-338,396-419,522-535`). KDE preserves the tile slot but skips the native write (`kwin/src/plan-adapter.ts:7549-7569,7605-7615`); Windows preserves the slot and writes at its projected origin with each extent at least the declared minimum, so overlap/overflow is possible (`crates/tiler-windows/src/tiling.rs:153-174`; `tiling_sys.rs:4917-4949`). Neither is a floating transition.
- **When [V]:** newcomers can themselves be infeasible or make existing siblings infeasible; larger gaps, smaller work areas/output relocation and changed minimum hints can also cause it. Along the split axis, required child/subtree minima plus gaps may exceed available space; across that axis, a leaf can exceed its cross extent. Shares are not globally optimized. Fresh fitting may decline to a sequential seed, but that seed is not guaranteed feasible (`crates/tiler-core/src/engine.rs:929-963,1053-1108`). Gap-budget rejection is separate from a minimum-size violation.
- **Later hints need adapter dispatch [V]:** KDE reads hints freshly when constructing requests (`kwin/src/plan-adapter.ts:2546-2609,5466-5475`), but its classifier does not compare hints and quiet equality can suppress dispatch (`:2354-2444,4954-4975`). No `minSizeChanged`/`maxSizeChanged` subscription was found in `plan-adapter-entry.ts`. Thus hint-only change is not an independently guaranteed replan; accompanying geometry/member/scope change or an explicit dispatching command can carry it. Windows' active tiled-domain reconcile builds rows with fresh hints and calls Engine without fingerprint-equality suppression on that path (`crates/tiler-windows/src/tiling_sys.rs:4716-4790`); gesture/suspend/mode/query-budget gates still apply. No new hint-trigger fix is implemented here.
- **Current float semantics [V/R]:** explicit float uses centered 60% on first use, retained geometry later; unfloat uses live geometry and fresh admission, never old-slot restoration (`kwin/src/plan-adapter.ts:2761-2842`; [float decisions](../../decisions.md#window-state-float-sticky-maximize-fullscreen)). Manual float/history is session-local. An automatic policy would need to distinguish automatic from user intent, honor minimums in its floating placement, define explicit unfloat and restart behavior, and preserve the subject's native focus.

| Option | Consequences: surprise, stability, float intent, restart and focus |
|---|---|
| Float newcomer only | Predictable admission exception, but cannot repair a pre-existing member made infeasible by the arrival or a later scope/hint change. Define whether rejection is based on the newcomer alone or any resulting infeasibility. Retain newcomer focus; do not substitute survivor focus. Centered-60% placement may itself be below the minimum. Unknown hints/restart can change admission classification; automatic return to tiling risks oscillation. |
| Float whichever member is infeasible | Can affect long-standing windows unexpectedly. Flagged leaves are not a minimal removal set: choose victim/order and reproject after each removal. Auto-retile on changed hints can oscillate. Need separate automatic provenance and manual-unfloat/restart rules; moving an unfocused victim must not steal focus. Highest policy/state cost. |
| Origin + minimum (Windows) | No float provenance or auto-retile oscillation; keep topology/focus and explicit float semantics. Visible placement is predictable, but overlap/overflow can obscure siblings and repeat after fresh adoption. |
| Skip writes (KDE) | No fighting or float transitions; focus/native frame remain, but reserved tile space need not match the window's actual position. Overlap and an apparently unplaced newcomer remain possible. Restart does not solve infeasibility. |

- **Recommendation:** do not automatically float arbitrary existing members. Preserve explicit float intent and the current behavior pending a selected fallback. If automatic floating is wanted, prefer a bounded admission-only fallback with no automatic retiling, and define restart/manual-unfloat behavior first. For fixed-tree infeasibility, origin+minimum is the simpler consistent placement option if the user accepts overlap/overflow. No optimizer or automatic-float policy is selected by this answer.

### Q3. Could admission-time unmaximize affect games?

- **Yes, it can change a maximized windowed game's or launcher's startup state; compatibility is unproven.** Fullscreen exemptions reduce the affected set, but are not a universal game detector. Leaving first-seen maxima alone would avoid this particular unsolicited native restore.
- **KDE fires [V]:** on an eligible maximized, non-fullscreen observed member with no known applied evidence (or a born-fullscreen held member first exiting to maximized) and no prior admission attempt. It marks the ID before `clearMaximize`, calls the native setter once, then refetches; a still-maximized/failed result does not cause another admission retry (`kwin/src/plan-adapter.ts:5330-5397`). Known retained members are exempt; the implementation uses `appliedById`, not a separate portable maximize slot. Foreground/hidden floating-domain gates precede clear (`:4883-4888,5192-5195`). The newly repaired explicit Meta+M activation is a separate path and does not change this admission set.
- **Windows fires [V]:** on otherwise eligible, identity/scope/proof-fenced maximized rows assigned to a tiled workspace, with no retained `member_rects` slot and no lifetime-bound admission attempt. Fullscreen wins, and attempted identities never automatically retry. It marks before nonactivating asynchronous placement restore; dispatch is not completion (`crates/tiler-windows/src/tiling.rs:550-583`; `tiling_sys.rs:3785-3908,3303-3335`). R-MAX-03 preserves first maxima slotless on floating workspaces; today's first tiled admission still clears them once. Born-fullscreen holds are exempt while fullscreen; exiting to a still-unslotted maximum reaches admission clear (`tiling_sys.rs:8620-8799`).

| Game/window shape | KDE [V] | Windows [V]; game-mode attribution TBD |
|---|---|---|
| Exclusive fullscreen | Exempt if KWin reports native fullscreen; actual game's flags/mode need user evidence | Exempt if observed fullscreen; Win32 caption/monitor geometry is not proof of exclusive presentation mode |
| Fullscreen-flagged borderless | Native `fullScreen` exempts it, including born hold | No equivalent KWin flag: captionless visible frame covering a full monitor is classified fullscreen |
| Output-sized borderless without fullscreen flag | Not inferred fullscreen. If maximize is false, no admission clear, but ordinary tiling can still resize it; if maximize is true, clear can fire | Captionless frame covering `rcMonitor` is inferred fullscreen and exempt, irrespective of zoom. Work-area-only or otherwise noncovering frame is not automatically fullscreen |
| Maximized windowed game/launcher | Eligible first admission can clear it unless exempt above | Eligible slotless first admission can clear it unless classified fullscreen above |

- Shape evidence: KDE reads `fullScreen`/`maximizeMode`, without output-size inference (`kwin/src/plan-adapter-entry.ts:844-845,1229-1230`); unreadable flags fail closed. Windows checks `WS_CAPTION`, `IsZoomed` and monitor containment (`crates/tiler-windows/src/tiling_sys.rs:592-610`; `tiling.rs:2966-2973`). Generic proof/hide eligibility is not the runtime maximize-clear gate.

| Option | Siblings, later restore, focus and compatibility consequence |
|---|---|
| Keep current one-shot clear | Normal fresh tiling/reflow on launch. Preserves current workflow but introduces a native startup restore; no game-compatibility guarantee. |
| Preserve with reserved tile | Admit a tiled slot beneath native maximize; siblings lose that allocation immediately, possibly behind the covering window. Later native unmaximize restores the current allocation. No launch restore, but initial projection must avoid fitting from the maximum frame. |
| Preserve slotless until native unmaximize | Keep workspace membership/focus/hide-reveal but no tile or intentional-float exception; siblings use the full layout. First native restore fresh-admits and reflows normally. Requires an explicit held lifetime and cancellation/removal semantics. This is a proposed extension, not today's R-MAX-03 first-tiled-clear behavior. |
| Later Preserve/Clear setting | Makes the tradeoff explicit. Define default and whether it applies only to future admissions; do not retroactively restore/clear already observed windows on setting changes. A setting is not a reliable game detector. |

- **Recommendation:** favor preserving first-seen maximized windows slotless until their native unmaximize, if the user chooses to change policy; it avoids unsolicited launch restore and wasted sibling slots. Expose an admission-only Preserve/Clear choice later if users need forced tiling. Do not infer a game-specific exception from size alone. This needs a separate implementation brief; current clear remains unchanged.
- **Anti-cheat [R only]:** [gaming record](../../changes/windows-gaming-coexistence.md#anti-cheat-assessment), lines 417-440, establishes no certification/allowlist or specific incompatibility. Installer-context LL hooks and separate overlays are not game DLL/render injection, but that does not establish acceptance; E8 `SendInput` is detectable injected input. Public placement/hiding APIs likewise do not guarantee compatibility. Preserving launch maximize removes one native action, not the other hooks/overlays/workspace actions.
- **This is not B9 overlaid-unfloat:** B9/R-FLT-06 concerns explicit unfloat of an already-intentionally-floating, maximized/fullscreen window. This question is first admission of a native maximum. The reply does not select either policy by implication.
