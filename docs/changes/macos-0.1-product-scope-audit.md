# macOS 0.1 product-scope audit vs Windows 0.1

**Status:** Audit complete; scope decisions pending. This record does not change either approved gate.

## Basis and reading key

- Scope rule: do not remove Windows-delivered functionality solely on macOS. Tabbed groups are deferred everywhere. A demonstrated capability or implementation barrier can go back to the user; a parked implementation or a test gap is not permission to cut a feature (`docs/decisions/macos.md:118-123`, `docs/decisions/visuals.md:76-82`).
- **Windows baseline:** the implemented 0.1 product, not an assertion that a 0.1 binary has been released. The Windows feature queue records offline delivery of the main slices (`docs/changes/archive/windows-win-drag-review.md:293-306`); the [Windows gate][W] and [physical checklist][WP] qualify native evidence. Both platform gates expressly distinguish approval from release acceptance (`docs/changes/windows-0.1-gate-proposal.md:3-5,159-172,174-196`, `docs/changes/macos-0.1-gate-proposal.md:3-5,180-189`). A gate-only requirement is marked as such, not counted as shipped behavior.
- **macOS baseline:** the original 2026-10-28 ROI review (`docs/changes/macos-world-v2-port.md:1517-1532,1713-1746`), the approved 2026-10-29 amendments, and later delivery/host-limit records. Implemented means product-path code exists; fixture, scoped, historical and offline passes do not substitute for release acceptance. The later D0 reaffirmed the release gate; its D1–D6 are distinct from the October gate decisions (`docs/changes/macos-v4-open-decisions-review.md:59-65`).
- **Decision column:** “Yes if cut” means retain current approved scope unless the user explicitly changes it. “Recorded limit” means a current difference is already documented; it is not evidence that a remaining gate check passed. **Gate** is the macOS approved gate dependency unless Windows is explicitly named. `[W]` and `[M]` identify the two numbered gates.

## Pending scope decisions and verification

1. **Indicator coverage:** decide whether multi-display indicator safe-hide is sufficient rather than per-output presentation. Per-window artwork is deferred past 0.1, and the default-off representative icon remains outside the 0.1 gate. The two-display workspace/reliability gates are unchanged.
2. **Windows user actions without selected macOS equivalents:** decide the portable browser/terminal shortcuts and project-owned fullscreen toggle. Keep app-owned exit safety separate. The documented sticky, keep-above/warp and automatic-fixed differences are capability limits, not new decisions here; specifically resolve any unmet sticky gate journey with the user rather than treating the capability limit as acceptance.
3. **Already-required work:** no new decision is needed to keep the gate. If proposing to ship without workspace scope choices, two-display transfers/migration, passive same-/cross-output drag, or real fullscreen carry, return with the demonstrated host blocker and proposed exact gate amendment. Same rule for any failed underlay attempt, native Settings, or persisted future tiling default. D1/D2 October host substitutions/K labels do not waive the corresponding M journeys; November D1/D2/D3 carve out only the stated host/proof limits.
4. **Not a Windows parity cut:** dynamic native radius, route pickers, virtual parking backend, the below-target active-border experiment, macOS 15 verification and the shelved tools. The fixed shared border-radius default of 6 is confirmed.

Verification was an offline records comparison with targeted settings/CLI/renderer source inspection where the records were ambiguous. No live or release acceptance was performed. This note stays active for the scope questions above.
